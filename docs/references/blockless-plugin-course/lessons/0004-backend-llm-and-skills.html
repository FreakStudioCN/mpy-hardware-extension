/v1/llm/messages：Skill、phase recipe 和 6 个工具如何变成模型请求

本课只讲后端。重点是 routes_llm.py 如何把完整 SKILL.md、协议适配器、phase recipe、resolved data 和 6 个工具喂给模型。

核心文件

  • mpyhw-api/app/routes_llm.py：LLM route、prompt、SSE translation、server-side codegen。
  • mpyhw-api/app/skill_catalog.py：served skills 白名单和 phase 映射。
  • mpyhw-api/app/tool_registry.py：后端协议工具 registry。
  • mpyhw-api/app/routes_tools.py：/v1/tools，给插件做版本检查。
  • mpyhw-api/tests/test_protocol_backend.py：后端协议层核心测试。

Skill 进入 prompt 的路径

request body carries phase
  -> routes_llm._phase(body)
  -> routes_llm._system_prompt(phase)
  -> skill_catalog.skill_md_body(phase)
  -> adapter preamble + full SKILL.md + phase recipe
  -> DeepSeek/OpenAI-compatible request

adapter preamble 的意义

上游 skill 往往按“本地 agent”写，比如让 agent 跑 shell、调用 mpremote、使用 AskUserQuestion。当前架构里模型没有本地文件和串口权限，所以 preamble 明确要求：

  • 读写文件用 file_operation。
  • 设备动作和 mpremote 用 device_command。
  • 脚本用 script_run。
  • 问用户用 approval_request。
  • 进度用 status_update。
  • 结束 phase 用 phase_complete。

phase recipe 的意义

recipe 是当前后端对每个 phase 的硬约束。例如 analyze 必须先发组件确认卡，而不是环境预检；generate 不直接运行脚本，而是写 firmware/main.py 的 intent；wiring/diagram 直接写 JSON；deploy 通过 device_command 驱动设备。

resolved data injection

在 select-hw、generate、wiring、diagram、deploy 等 phase，后端会把 board profile、driver contexts、current manifest 注入 prompt。这样插件侧不需要重新实现 package ranking 或 driver-context extraction。

server-side codegen

model emits:
file_operation({
  op: "write",
  path: "firmware/main.py",
  intent: "..."
})

routes_llm.py intercepts firmware/*.py
  -> nested codegen prompt
  -> fills content
  -> forwards file_operation with real code

验收点：只允许拦截 firmware/*.py，不能对奇怪路径烧 codegen 预算。

改 skill 后最容易出错：模型把 skill 里的本地 shell 步骤照字面输出。验收时必须看 smoke/e2e 是否出现 raw shell smell、旧工具名或无关 preflight。
