1. 总体模型：云端是脑，插件是手和屏幕

当前设计里，Blockless 不是一个纯前端插件，也不是后端直接操作用户电脑。它被拆成四层：Webview UI、VS Code 扩展宿主、云端 API、Python shim。最重要的边界来自 docs/specs/CURRENT-DECISIONS.md：agent loop 在 VS Code extension 内；mpyhw-api 做 auth、credits、LLM provider proxy、board/package/tool content、telemetry；Python shim 只做本地设备 IO。

用户输入一句硬件需求
Webviewindex.html 发 start_session
Panel Hostpanel.ts 鉴权、建 loop
Controller管理状态、prompt、artifact
Protocol Loop把 SSE tool call 转成本地动作
API/v1/llm/messages 调模型、计费、注入上下文
6 ToolsUI/FS/Host/Device/Notify
Shimmpremote、烧录、串口、脚本
项目blockless-project 生成文件
学习抓手：以后看代码时，不要先钻进某个函数。先问“这个问题属于 UI、宿主、协议、后端还是设备？”。边界判断对了，读代码会快很多。

2. 插件如何启动

VS Code 插件入口由 mpy-hardware-extension/package.json 决定。官方文档把它叫 extension manifest：每个 VS Code extension 都需要根目录 package.json，其中 main 指向扩展入口，contributes 声明插件往 VS Code 增加什么能力。

清单字段本插件当前值/作用该读什么
main./dist/extension/activate.cjs，打包后的激活入口src/extension/activate.ts
contributes.viewsContainersActivity Bar 增加 mpyhw 容器，标题 BlocklessVS Code Contribution Points
contributes.views在 mpyhw 容器里放 mpyhw.panel Webview ViewcreateViewProvider
contributes.commands注册 mpyhw.openPanelcommands.ts
contributes.configurationmpyhw.apiBaseUrl、pythonPath、pipIndexUrlapi-base-url.ts、device-shim.ts

activate.ts 做的事情很少，这是好事：创建输出通道，创建 WebviewViewProvider，注册 mpyhw.panel，再注册一个打开面板的命令。真正的业务总线在 src/webview/panel.ts。

activate()
  -> createViewProvider()
  -> registerWebviewViewProvider("mpyhw.panel", provider)
  -> registerCommands("mpyhw.openPanel")

3. 一次生成会话发生了什么

Webview 页面加载后会立即向宿主发两个消息：request_boards 拉真实板卡列表、后端模式和 credits；run_doctor_check 做环境检测。用户点击 Generate 后，Webview 发 start_session，由 panel.ts 接住。

启动前

panel.ts 会解析 API base URL，创建设备 shim，创建 GitHub auth，并确定项目输出目录。打开 workspace 时写到 <workspace>/blockless-project；没打开 workspace 时使用扩展的 globalStorage fallback。

会话开始

start_session 分支先检查协议版本 /v1/tools，再强制 GitHub 登录换后端 JWT，然后调用 controller.start({ intent, boardId: "auto" })。

会话运行

SessionController 把 onEvent、confirmApproval、signal、recorder 等依赖传给 loop。它也负责 retry、cancel、reset，避免多个会话把状态互相覆盖。

产物落盘

真实协议路径通常由 loop 通过 write_project_file/file_operation 实时写入，SessionController 收到 file_written 后只报告路径，不再重复批量写。

为什么要有 SessionController？

因为 Webview、LLM stream、用户确认、文件写入、取消重试是异步交错的。SessionController 用 AbortController、generation、pendingPrompts 和保存的 state 保证：并发 start 会被拒绝；reset 后旧会话的迟到消息不会落到新会话；用户回答可以准确回到正在等的 tool result。

4. 协议：旧工具很多，新路径只给模型 6 个工具

当前核心是 contracts/protocol_messages.json。扩展侧 protocol-registry.ts 读取这个契约，把 LLM 可用工具映射到 5 条执行通道：ui、fs、host、device、notify。

协议工具阻塞？插件执行通道效果
approval_request是UIWebview 渲染 rich card，用户选择后回传 ui_prompt_response
device_command是Device转给 DeviceShim，执行 scan、cp、soft_reset、stream 等
file_operation是FS读写项目文件，路径由 workspace-writer.ts 限制
script_run是Host跑 validate、scaffold、static check、simulate、render 等工具链脚本
status_update否Notify时间线进度，插件自动 ack
phase_complete否Notify结束 phase，更新 manifest，自动进入下一 phase 或停止

runProtocolBuild 的循环很机械：按 phase 调 /v1/llm/messages，收 SSE，积累 tool_use_complete，执行工具，把 tool_result 回塞进下一轮 messages。如果某个 phase 发了 phase_complete，就根据 next_phase 自动进入下一阶段。

for phase in analyze/select-hw/generate/wiring/diagram/deploy:
  POST /v1/llm/messages with phase + manifest + tools
  collect tool calls from SSE
  execute each tool locally
  send tool_result back in next turn
  if phase_complete: carry manifest and advance
容易混淆：src/core/tool-registry.ts 里还保留旧的 canonical 27-tool 路由，用于 legacy agent-backed loop 和历史测试。当前 createLoop() 默认返回 createProtocolLoop()，课程重点是 6-tool protocol path。

5. 后端边界：它不碰你的电脑，但它决定每个 phase 怎么走

mpyhw-api/app/main.py 注册了 health、packages、content、tools、llm、auth、credits、telemetry 等路由。插件直接依赖的关键接口如下：

接口插件何时调用作用
GET /v1/boardsWebview 加载时返回 builtin/community board 列表
GET /v1/healthWebview 加载时显示 live/stub server mode
POST /v1/auth/githubstart/retry 前用 VS Code GitHub access token 换后端 JWT
GET /v1/credits加载时静默获取显示余额和每日 grant
GET /v1/toolsstart 前检查 protocol_version 是否匹配
POST /v1/llm/messages每个 protocol turnSSE 返回模型文本、thinking、tool calls、credits
/v1/packages/*后端内部和旧工具路径搜索包、resolve、读取 driver context

routes_llm.py 是最密集的后端文件。它做四类重要事情：

协议适配

把 phase skill 和 protocol recipe 拼成 system prompt，要求模型只能发 6 个协议工具。

安全与计费

检查工具白名单、用户 JWT、并发 session、credits、LLM upstream circuit breaker。

上下文注入

在 select-hw/generate/wiring/diagram/deploy 等 phase 注入 board profile、driver contexts、current manifest。

服务端代码生成

当模型对 firmware/*.py 发 file_operation 且只给 intent 时，后端用更聚焦的 codegen prompt 填入 content。

6. 代码阅读路线：按任务读，不要从头读

下面是维护这个插件最有用的阅读顺序。每一组都对应一个真实开发任务。

任务 A：理解插件如何进入 VS Code

mpy-hardware-extension/package.json → src/extension/activate.ts → src/extension/commands.ts → VS Code 官方 manifest/contribution points/commands 文档。

任务 B：理解 UI 与宿主通信

src/webview/index.html 搜 postMessage 和 window.addEventListener("message"；再读 src/webview/panel.ts 的 webview.onDidReceiveMessage。两边消息类型必须对齐。

任务 C：理解生成流程

panel.ts:createLoop → src/core/protocol-build.ts → src/core/protocol-loop.ts → src/core/llm-client.ts → mpyhw-api/app/routes_llm.py。

任务 D：理解协议契约

contracts/protocol_messages.json → src/core/protocol-registry.ts → mpyhw-api/app/tool_registry.py → mpyhw-api/app/routes_tools.py。

任务 E：理解本地设备部署

src/extension/device-shim.ts → src/extension/shim-process.ts → python/shim/serve.py → Doctor 相关 runDoctor 和 Webview Doctor 渲染。

任务 F：理解文件写入安全

src/extension/workspace-writer.ts → panel.ts:makeWorkspaceWriter → SessionController.writeArtifactsIfReady。重点看 path allowlist、workspace containment、blockless-project 输出目录。

7. 开发与验证：最小闭环

本仓库已经有大量测试。小改动优先跑最贴近的测试，再跑整体命令。常用命令：

你改了什么先跑再跑
Webview DOM/UInode --no-warnings --experimental-strip-types --test test/webview-dom.test.tsnpm test
panel/session/protocolnode --no-warnings --experimental-strip-types --test test/session-controller.test.ts test/protocol-loop.test.tsnpm run typecheck
文件写入node --no-warnings --experimental-strip-types --test test/workspace-writer.test.tsnpm test
设备 shimnode --no-warnings --experimental-strip-types --test test/shim-process.test.ts test/device-shim.test.ts真实设备 smoke
后端路由pytest mpyhw-api/tests/test_*.py后端全量 pytest
发布前npm test && npm run typechecknpm run package 或 publish skill 预检

如果你要本地跑完整开发栈，本仓库有 dev-up skill：它会启动 Postgres、mpyhw-api、探活 /v1/health//v1/boards，再加载 VS Code 扩展。只想用线上 Render 后端测本地扩展，则用 cloud-test skill。

开发原则：一次只改一个边界。比如 UI 卡片文案不应该顺手改协议 schema；设备扫描问题不应该顺手重写 LLM prompt。这样测试和回滚都简单。
