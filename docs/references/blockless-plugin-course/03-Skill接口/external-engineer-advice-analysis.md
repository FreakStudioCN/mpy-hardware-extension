# “协议不能只是给前端渲染 UI 的消息格式”到底是什么意思

这句话如果用大白话说，就是：

**你们现在要设计的，不应该只是“后端告诉前端显示一个卡片、前端回一个按钮结果”的聊天格式。**

**你们真正需要的是一套“项目任务怎么开始、怎么往下做、做到哪一步了、失败了怎么继续、谁来执行、结果怎么回传”的工作流规则。**

换句话说：

- UI 消息协议，关注的是“界面怎么显示”
- 工作流协议，关注的是“事情怎么真正做完”

你们现在的问题，恰恰都不是“卡片长什么样”造成的，而是“流程做到一半断了以后，系统不知道自己做到哪一步、下一步该找谁干、能不能继续”。

---

## 1. 先讲一个最简单的类比

假设你点外卖。

如果系统只有 UI 消息协议，它可能只有这些消息：

```text
show_status("商家已接单")
show_status("骑手已到店")
show_status("配送中")
show_button("确认收货")
```

这只能让页面“显示得像回事”。

但如果骑手中途车坏了、订单超时、商家缺货、你改地址了，这套东西就不够了。

真正的外卖系统还需要一整套工作流信息，比如：

- 订单号是多少
- 这是哪个用户的哪一单
- 当前卡在哪一步
- 商家是否已经出餐
- 骑手是否已经取货
- 这一步失败后能不能重试
- 用户取消后钱怎么退
- 骑手重发一次“已取货”会不会重复扣款

这部分才是“工作流协议”。

所以：

**UI 消息像是页面提示语。**

**工作流协议像是外卖系统后台真正流转订单的那张工单。**

---

## 2. 为什么你们这个项目不能只做 UI 消息协议

你们的插件不是普通聊天面板，而是在做一条很长的硬件生成流水线：

```text
用户一句话需求
-> 分析器件
-> 找驱动
-> 选板子
-> 分配引脚
-> 生成项目骨架
-> 生成代码
-> 仿真 / 静态检查
-> 烧录设备
-> 看设备输出
-> 出错再修
-> 生成接线图 / 架构图
-> 冷门驱动生成
-> 打包发布到 upypi
```

这不是“发几条消息就完了”的事情。

这是一条**会中断、会失败、会回退、会跳步骤、会等用户确认、会调用本地文件、会调用设备、会调用脚本**的长流程。

所以你们需要的不只是：

```text
后端 -> 前端：显示一个确认卡片
前端 -> 后端：用户点了确认
```

而是需要：

```text
这是谁的会话
现在在第几个阶段
这一阶段做到哪一步了
这一步是谁执行
执行成功了吗
失败能不能重试
断了以后能不能继续
已经写过的文件要不要重复写
已经发过的烧录命令要不要再发
用户取消之后怎么收尾
```

这才叫“工作流协议”。

---

## 3. 你们现在遇到的问题，为什么本质上都是工作流问题

你们现在列的几个痛点，我翻译成工作流语言大概是这样。

### 3.1 “分析完器件后没反应了”

表面看像 UI 没刷新。

但本质问题通常是：

- 系统没有明确记录“当前已经完成 analyze，下一步应该进入 select-hw 还是 gen-driver”
- 或者已经发出了某个动作，但没收到结果，不知道该继续还是该报错
- 或者 LLM 说了一段话，但没有真正发出下一步动作

这不是页面显示问题。

这是“流程状态机不完整”。

### 3.2 “冷门硬件没有现成驱动就停了”

表面看像后端能力不够。

但本质问题通常是：

- 协议里没有规定“找不到驱动时要切到 `gen-driver` 阶段”
- 没有定义这个阶段需要哪些输入
- 没有定义 PDF / Arduino / GitHub URL 这些资料怎么传给它
- 没有定义它失败时是 `failed` 还是 `partial`
- 没有定义没板子时怎么保存进度

这不是单纯“模型笨”。

这是“工作流里压根没这条分支，或者分支定义不完整”。

### 3.3 “生成了代码但板子跑不起来，不知道哪一步错”

表面看像错误提示不够好。

但本质问题通常是：

- 没有结构化记录每一步的输入输出
- 没有结构化记录哪个脚本生成了哪个文件
- 没有结构化记录哪个设备命令在哪一步执行
- 没有结构化记录错误属于 `可重试`、`需人工处理`、`需接线检查`

所以最后只能看到一句：

```text
失败了
```

而不是：

```text
失败在 deploy 阶段的 hardware_sanity 步骤
I2C scan 为空
建议检查 SDA/SCL、供电、上拉电阻
可以重试 3 次
或者保存当前进度稍后继续
```

这就是工作流协议和“报错字符串”的区别。

### 3.4 “上传了 PDF 或 Arduino 代码也不知道怎么利用”

表面看像插件没做上传。

但本质问题通常是：

- 没有定义资料上传属于哪个阶段
- 没有定义上传后怎么进预处理脚本
- 没有定义预处理结果怎么回传
- 没有定义预处理结果写到哪里
- 没有定义下一步是谁消费这个结果

所以资料虽然“进来了”，流程却不知道下一步怎么接。

这依然不是 UI 问题。

这还是工作流问题。

### 3.5 “驱动写完了，但没有打包发布到 upypi 的收尾步骤”

表面看像少写了几个文件。

但本质问题通常是：

- 协议里没有一个 `publish` 阶段
- 没定义它的输入是什么
- 没定义它要生成哪些产物
- 没定义上传前是否需要用户确认
- 没定义“不上传也要完整交付本地包目录”

所以驱动做完以后，系统只能停在“文件生成好了”，但不能形成“项目闭环”。

### 3.6 “没有中间确认点，出错后只能重来”

表面看像少几个弹窗。

但本质问题通常是：

- 没有 checkpoint
- 没有 resume
- 没有 session 持久化
- 没有这一步的产物登记
- 没有“失败但可继续”的标准输出

所以一断就只能从头再来。

这就是最典型的“你缺的是工作流协议，不是 UI 消息”。

## 4. 什么叫“UI 消息协议”

先把这个概念讲清楚。

UI 消息协议通常只关心：

- 显示什么
- 用户点了什么
- 界面要不要刷新

比如：

```json
{
  "type": "approval_request",
  "payload": {
    "header": "确认器件清单",
    "items": ["AHT20", "OLED", "LED"]
  }
}
```

前端收到后：

- 画一个卡片
- 列出器件
- 给一个确认按钮

用户点完后：

```json
{
  "type": "approval_response",
  "payload": {
    "confirmed": true
  }
}
```

这就结束了。

这种协议当然有用，但它只够干“交互显示”这件事。

它没有回答这些更关键的问题：

- 这是哪个项目的确认卡片
- 这张卡片对应哪个阶段
- 这是第几步
- 如果用户稍后再来，这张卡片还能不能继续
- 用户确认后下一步是谁来执行
- 如果确认消息重复发了一次会怎样

所以，**UI 消息协议只是工作流协议的一小部分。**

---

## 5. 什么叫“工作流协议”

工作流协议关心的是：

**一件复杂事情，从开始到结束，整个流转过程怎么可靠地推进。**

它至少要解决下面这些问题。

### 5.1 这是谁的任务

要有 `session_id`。

大白话就是：

```text
这是“这一次造硬件任务”的唯一编号
```

否则：

- 插件重启后不知道之前那次任务是谁
- 后端也不知道哪条消息属于哪次项目

### 5.2 现在做到哪一步

要有：

- `phase`
- `step_id`

大白话就是：

```text
现在是在 analyze 阶段
还是 gen-driver 阶段
是在“提取 PDF”
还是“验证硬件”
还是“发布 upypi”
```

没有这个信息，出错后你连“卡在哪”都说不清。

### 5.3 这一步是谁执行

要有明确动作类型，比如：

- `file_operation`
- `script_run`
- `device_command`
- `approval_request`

大白话就是：

```text
这一步到底是让插件写文件
还是让插件跑脚本
还是让插件操作设备
还是让用户确认
```

### 5.4 做完没做完

要有明确结果，比如：

- `success`
- `partial`
- `failed`

这里的重点是 `partial`。

大白话就是：

```text
这一步没完全做完
但已经做出一些产物
而且以后还可以从这里继续
```

这对你们很关键，因为你们很多问题都不是“完全失败”，而是“做到一半断了”。

### 5.5 失败以后能不能继续

要有：

- `checkpoint`
- `resume_from`

大白话就是：

```text
已经生成了调试版驱动
设备现在没连上
你可以下次从“硬件验证”这一步继续
不用从 analyze 再来一遍
```

这才是真正解决“只能重来”的关键。

### 5.6 重发一次会不会出事

要有：

- `idempotency_key`

这词很拗口，但意思很简单：

```text
如果同一个命令因为断线、重试、超时又发了一遍
不要把同一个副作用执行两次
```

举例：

- 同一个文件不要重复覆盖
- 同一个 upypi 发布不要重复发
- 同一个烧录不要重复跑

### 5.7 超时怎么办

要有：

- `timeout_ms`

大白话就是：

```text
这个动作最多等 30 秒
超过就别傻等
要返回“超时”
```

这直接关系到“分析完器件后没反应”这种问题。

### 5.8 能不能重试

要有：

- `retryable`
- `attempt`
- `max_attempts`

大白话就是：

```text
这次失败能不能再来一次
已经试了几次
最多还能试几次
```

### 5.9 生成了什么东西

要有：

- `artifacts`

大白话就是：

```text
这一阶段到底生成了哪些文件、日志、图、报告
```

不然用户和工程师都不知道该看什么。

### 5.10 错误到底是什么意思

要有结构化错误，不只是一个字符串。

比如别只返回：

```json
{
  "errors": ["失败了"]
}
```

而要返回：

```json
{
  "errors": [
    {
      "code": "i2c_scan_empty",
      "message": "I2C scan returned no devices",
      "retryable": true,
      "suggested_actions": [
        "检查 SDA/SCL 是否接反",
        "检查 3.3V 供电",
        "检查是否需要上拉电阻"
      ]
    }
  ]
}
```

这才是用户能排查的问题描述。

## 6. 你们这个项目里，工作流协议应该长什么样

如果用你们的项目语境，大概可以把协议理解成：

**服务器端像“项目经理 + 技术负责人”**

**插件像“现场执行员 + 展示面板”**

服务器端决定：

- 现在做哪个 phase
- 下一步该写文件还是跑脚本还是操作设备
- 失败后是重试、跳过、还是保存断点
- 冷门硬件是不是要进入 gen-driver
- PDF/Arduino 材料够不够
- 驱动写完是不是该进入 publish

插件只负责：

- 把消息渲染成 UI
- 真正去读写文件
- 真正去跑白名单脚本
- 真正去跑 mpremote / 设备命令
- 把结果按协议发回去

这里的关键不是“前后端分工”这句话本身，而是：

**分工必须写进协议里，而不是靠双方脑补。**

## 7. 你们现在的 7 类消息，为什么还不够

你们现在草案里已经有这些消息：

- `approval_request`
- `status_update`
- `file_operation`
- `script_run`
- `device_command`
- `stream`
- `phase_complete`

这已经比很多项目强了。

但为什么还说“不能只设计成 UI 消息格式”？

因为光有消息类型，还不够。

还需要给这些消息加“工作流语义”。

也就是要补这些东西：

- `protocol_version`
- `session_id`
- `correlation_id`
- `phase`
- `step_id`
- `checkpoint`
- `resume_from`
- `timeout_ms`
- `retry`
- `idempotency_key`
- `permission`
- `artifacts`
- `structured errors`

没有这些字段时，你的消息虽然“能显示、能执行”，但还不能稳定地支撑长流程。

所以更准确地说：

**你们现在的 7 类消息，是工作流协议的“动作类型”。**

**但还缺“生命周期字段”和“恢复语义”。**

---

## 8. 为什么这和 thin plugin 有直接关系

你们现在想把插件做薄，这是对的。

但要注意：

**thin plugin 不等于 dumb plugin。**

也就是：

- 插件可以不做嵌入式业务判断
- 但插件不能没有工作流边界和安全边界

插件至少还得懂这些事：

- 这是哪个 session 的消息
- 这是请求还是响应
- 这个动作有没有超时
- 这个动作是不是高风险，需要用户确认
- 这个动作是不是执行过了，不能重复执行
- 这个路径能不能写
- 这个脚本是不是白名单

所以“thin plugin”的正确理解是：

```text
插件不做业务决策
但插件必须可靠地执行工作流协议
```

---

## 9. 用一句更容易懂的话总结

如果只设计 UI 消息协议，你们得到的是：

```text
一个会说话、会弹卡片、会显示进度的界面
```

如果设计成真正的工作流协议，你们得到的是：

```text
一套能把“硬件项目生成”这件复杂事真正跑完、跑稳、跑得可恢复的执行系统
```

前者解决的是“怎么显示”。

后者解决的是“怎么做成”。

你们现在缺的明显是后者。

## 10. 直接落到你们项目上的建议

如果把这句话转成你们现在最该做的事情，我建议就是这 6 条：

### 10.1 不要只定义消息类型，要定义统一消息信封

每条消息至少统一带：

- `protocol_version`
- `session_id`
- `msg_id`
- `correlation_id`
- `phase`
- `step_id`
- `timestamp`

这样消息才不是“散的”。

### 10.2 每个 phase 都必须定义三种结束状态

- `success`
- `partial`
- `failed`

尤其要把 `partial` 当一等公民。

因为你们的真实场景里，“做到一半断掉”比“彻底失败”更常见。

### 10.3 每个可能中断的 phase 都要有 checkpoint/resume

尤其是：

- `analyze`
- `gen-driver`
- `deploy`
- `publish`

不然你们的“稍后继续”永远只是口号。

### 10.4 每个本地执行动作都要有 timeout/retry/idempotency

重点包括：

- `file_operation`
- `script_run`
- `device_command`

这三个是最容易把流程拖死或重复执行的地方。

### 10.5 错误要结构化，不要只返回一句话

至少带：

- `code`
- `message`
- `retryable`
- `suggested_actions`

不然你们永远解决不了“代码跑不起来但不知道哪步错”。

### 10.6 先打通 3 个关键 phase

先不要一口气覆盖所有 phase。

最值得优先打通的是：

- `analyze`
- `gen-driver`
- `publish`

因为它们正好对应你们最痛的三个问题：

- 入口分析
- 冷门硬件
- 发布收尾

---

## 11. 最后一句

“不要把协议只设计成给前端渲染 UI 的消息格式”，翻译成最朴素的话就是：

**别只管‘页面显示了什么’，要先把‘事情怎么完整做完’这套规则设计清楚。**

因为对你们这个项目来说，真正难的从来不是“弹一个卡片”，而是：

**流程断了以后，系统还能不能知道自己做到哪了，并且从那里接着干。**
